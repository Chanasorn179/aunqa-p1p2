# V&V Strategy — ระบบบริหารจัดการหลักฐาน QA และผังเชื่อมโยงผลลัพธ์การเรียนรู้ (AUN-QA P1–P2)

ทีม Syntax Error 3 · ENGSE601 · ฉบับ 1.0 · อ้างอิง SE02 (FR-01–FR-10, NFR-01–NFR-10)

## 1. ระดับความสำคัญของระบบ (Integrity Level ตาม IEEE 1012)

**ระดับระบบโดยรวม: Level 2** — ถ้าระบบผิดพลาด ผลเสียจะอยู่ที่ความถูกต้องของข้อมูลประกันคุณภาพและเวลาของอาจารย์ ไม่กระทบชีวิต ความปลอดภัย หรือเงิน และยังมีคนตรวจซ้ำก่อนใช้ผลจริง เพราะอาจารย์เป็นผู้รับรองผล ส่วนระบบไม่ได้ตัดสินผล QA เอง

**ส่วนที่ยกขึ้นเป็น Level 3** เพราะถ้าผิดแล้วจะไม่มีใครเห็น และผลจะไปถึงรายงาน SAR ที่ส่งผู้ประเมินภายนอก

| ส่วน | ผลเสียเมื่อผิด |
|---|---|
| RBAC / การยืนยันตัวตน (FR-01, 02, NFR-04) | ผู้ไม่มีสิทธิ์อนุมัติหรือแก้หลักฐานได้ |
| Workflow หลักฐาน draft→submitted→reviewed→approved/revision (FR-04) | หลักฐานข้ามขั้นตอน หรือถูกนับว่า "รับรองแล้ว" ทั้งที่ยังไม่ได้รับรอง |
| Coverage / Mapping Gap, I/R/M (FR-07, 08) | รายงานว่า PLO ครอบคลุมครบทั้งที่ยังขาด ทำให้หลักสูตรตกเกณฑ์ P2 |
| Audit trail / version (NFR-05, 06) | ตรวจย้อนไม่ได้ว่าใครเปลี่ยนอะไร |

## 2. ระดับการทดสอบ × ส่วนของระบบ × Sprint × เครื่องมือ

| ระดับ | ส่วนที่ทดสอบ | Sprint | เครื่องมือ |
|---|---|---|---|
| Unit | กฎ workflow (state machine), สูตร coverage/I-R-M, ตัวตรวจสิทธิ์, validator ข้อมูลนำเข้า | S1–S4 (ทุก PR) | Vitest/Jest, coverage (istanbul) |
| Component | หน้า Matrix PLO–CLO, ฟอร์มอัปโหลดหลักฐาน, Dashboard | S2–S4 | React Testing Library |
| Integration / API | REST API ของ P1, P2, Shared (Auth, Audit) + PostgreSQL ที่ seed ด้วย fixture | S2–S4 | Supertest, Docker Postgres, Postman/Newman |
| System (E2E) | UC-01–UC-07 ครบเส้นทาง เช่น อัปโหลด→ตรวจ→อนุมัติ→เชื่อมกับ CLO→Coverage→Export | S3–S4 | Playwright |
| NFR | NFR-01/02 (ตอบสนอง ≤3 วิ/≤2 วิ), NFR-04 (สิทธิ์รายบทบาท) | S4 | k6, Playwright (เมทริกซ์บทบาท × endpoint) |
| Acceptance (UAT) | Acceptance Criteria ของแต่ละ FR กับอาจารย์ผู้ใช้จริง 5 บทบาท | S4 | สคริปต์ UAT + แบบบันทึกผล |

*Sprint ที่ใช้ (ปรับได้):* S1 Auth/RBAC + ข้อมูลหลักสูตร · S2 หลักฐาน + Workflow · S3 Mapping/Coverage + Gap/CQI · S4 Dashboard/Export + NFR/UAT

## 3. การทวนสอบเชิงสถิต (Static V&V)

- **ทบทวน SRS:** ใช้ checklist ของรายวิชา และทบทวนไขว้ทีมในครั้งที่ 3 ตรวจว่าทุก FR มี UC, Acceptance Criteria และ TC ใน RTM ครบ และไม่มี NFR ที่วัดผลไม่ได้
- **ทบทวนการออกแบบ (SDD + openapi.yaml):** walkthrough ในครั้งที่ 4 ตรวจว่า endpoint ตรงกับ FR ทุกข้อ ว่า state diagram ของ workflow ไม่มีทางข้ามขั้น และว่าโมดูล P1/P2 ไม่เข้าถึงตารางของอีกโมดูลโดยตรง
- **PR review:** ทุก PR ต้องมีผู้รีวิวอย่างน้อย 1 คนที่ไม่ใช่ผู้เขียน และ branch `main` ถูกป้องกันไว้ ส่วน Level 3 (หัวข้อ 1) ต้องมีผู้รีวิว 2 คน
- **Static analysis ใน CI:** ESLint + Prettier, `tsc --strict`, `npm audit` และ Semgrep (กฎความปลอดภัยของ Node/Express) รันทุก PR และถ้าผิดจะ merge ไม่ได้

## 4. สิ่งที่ตั้งใจไม่ทดสอบ และเหตุผล

| ไม่ทดสอบ | เหตุผล |
|---|---|
| ระบบของทีม P3–P6 และแหล่งข้อมูลภายนอก (ทะเบียน, HR, LMS) | อยู่นอกขอบเขต ทดสอบเฉพาะ "สัญญา" การนำเข้า/ส่งออกด้วย fixture CSV/JSON ตาม IF01–IF09 |
| SSO และ microservices | Blueprint V1 ไม่บังคับ และไม่ได้นำมาใช้ |
| ภายในไลบรารีบุคคลที่สาม (React, Express, ORM, ตัวสร้าง PDF) | เชื่อถือผู้พัฒนาไลบรารี ทดสอบเฉพาะส่วนที่เราใช้ผ่าน integration test |
| Load จริงที่ระดับ production (NFR-09: 100 ผู้ใช้พร้อมกัน) และ HTTPS/backup บนเซิร์ฟเวอร์จริง (NFR-03, 08) | ยังไม่มีสภาพแวดล้อม production จะทดสอบโหลดขนาดเล็กด้วย k6 บนเครื่อง dev และระบุผลไว้เป็นข้อจำกัด |
| ความถูกต้องเชิงวิชาการของ mapping (เช่น CLO นี้ควรเป็น R หรือ M) | เป็นการตัดสินของอาจารย์ ระบบทวนสอบได้เพียงว่าคำนวณและแสดงผลตามข้อมูลที่ใส่อย่างถูกต้อง |
| เบราว์เซอร์อื่นนอกจาก Chrome/Edge รุ่นล่าสุด และอุปกรณ์มือถือรุ่นเก่า | ทรัพยากรจำกัด จะตรวจ responsive (NFR-07) เฉพาะขนาดจอมาตรฐาน 3 ขนาด |
| ข้อมูลส่วนบุคคลจริงของนักศึกษา/อาจารย์ | ใช้ข้อมูลสังเคราะห์ทั้งหมด (สอดคล้องกับ D12) |
