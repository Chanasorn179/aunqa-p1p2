# V&V Strategy — ระบบ AUN-QA P1–P2 (Team Syntax Error 3)

> ENGSE601 D06 · ฉบับ 1.0 · 25 พ.ย. 2569 · อ้างอิง `docs/SRS_AUNQA_P1P2_v0.1.pdf` (F-01–F-08, FR-01.01–FR-08.07, NFR-01–NFR-12)

## 1. ระดับความสำคัญของระบบ (Integrity Level ตาม IEEE 1012)

**ระดับระบบโดยรวม: Level 2** — ถ้าระบบผิดพลาด ผลเสียจะอยู่ที่ความถูกต้องของข้อมูลประกันคุณภาพและเวลาของบุคลากร ไม่กระทบชีวิต ความปลอดภัย หรือเงิน และยังมีคนตรวจซ้ำก่อนใช้ผลจริง เพราะอาจารย์เป็นผู้รับรองผล ส่วนระบบไม่ได้ตัดสินผลการประเมิน AUN-QA เอง (SRS 1.2 นอกขอบเขต)

**ส่วนที่ยกขึ้นเป็น Level 3** เพราะถ้าผิดแล้วจะไม่มีใครเห็น และผลจะไปถึงรายงาน SAR ที่ส่งผู้ประเมินภายนอก

| ส่วน | ผลเสียเมื่อผิด |
|---|---|
| F-01 บัญชีและสิทธิ์ (FR-01.06, NFR-05, NFR-06) | ผู้ไม่มีสิทธิ์อนุมัติ แก้ หรือเห็นหลักฐานได้ |
| F-03 ลำดับสถานะการตรวจทานหลักฐาน | หลักฐานข้ามขั้น หรือถูกนับว่า "อนุมัติแล้ว" ทั้งที่ยังไม่ได้อนุมัติ |
| F-06/F-07 Mapping I/R/M และ Coverage | รายงานว่า Sub-PLO ครอบคลุมครบทั้งที่ยังขาด |
| Audit log และความสมบูรณ์ของข้อมูล (NFR-07, NFR-08) | ตรวจย้อนไม่ได้ว่าใครเปลี่ยนอะไร หรือข้อมูลนำเข้าซ้ำ / ไฟล์เพี้ยน |

## 2. ระดับการทดสอบ × ส่วนของระบบ × Sprint × เครื่องมือ

| ระดับ | ส่วนที่ทดสอบ | Sprint | เครื่องมือ |
|---|---|---|---|
| Unit | กฎเปลี่ยนสถานะ (F-03), สูตร Coverage (F-07), ตัวตรวจสิทธิ์ (F-01), ตัวตรวจไฟล์นำเข้า CSV (F-05) | S1–S4 ทุก PR | Vitest/Jest + coverage (เป้า ≥80% ส่วน Coverage ตาม NFR-12) |
| Component | ฟอร์มอัปโหลดหลักฐาน, ผัง Mapping, แดชบอร์ด | S2–S4 | React Testing Library |
| Integration / API | API ของ P1, P2 และบริการส่วนกลาง กับ PostgreSQL ที่ seed ด้วยข้อมูล มคอ.2; เมทริกซ์สิทธิ์ภาคผนวก ค (NFR-06) | S2–S4 | Supertest, Docker Postgres |
| System (E2E) | UC-01–UC-07 ครบเส้นทาง; เบราว์เซอร์และความกว้างจอตาม NFR-11 | S3–S4 | Playwright (Chromium, Firefox, WebKit) |
| NFR | NFR-01–03 ประสิทธิภาพ, NFR-07 audit, NFR-08 นำเข้าซ้ำ/checksum, NFR-09 กู้คืน | S4 | k6, สคริปต์ตรวจ checksum, ซ้อมกู้คืน |
| Acceptance (UAT) | NFR-10: ผู้ใช้ตัวแทน 5 คน × 3 งาน (DEP-03) | S4 | สคริปต์ UAT + แบบบันทึกผล |

*Sprint (ปรับตามแผนทีมได้):* S1 F-01 + F-05 · S2 F-02 + F-03 · S3 F-06 + F-07 + F-04 · S4 F-08 + NFR + UAT

## 3. การทวนสอบเชิงสถิต (Static V&V)

- **ทบทวน SRS (CP1):** ใช้ checklist ของรายวิชาและการทบทวนไขว้ทีม ตรวจว่าทุก FR วัดผลได้ มีเกณฑ์ยอมรับ และมี BR, UC และวิธีทวนสอบใน RTM บทที่ 7 ครบ รวมถึงติดตามการปิด TBD-01–TBD-06
- **ทบทวนการออกแบบ (D08: SDD + `openapi.yaml`):** walkthrough ตรวจว่า endpoint ครอบคลุมทุก FR ว่า state diagram ของ F-03 ไม่มีทางข้ามขั้น และว่า P1/P2 เรียกกันผ่านบริการส่วนกลางเท่านั้น
- **PR review (D09):** ทุก PR ต้องมีผู้รีวิวอย่างน้อย 1 คนที่ไม่ใช่ผู้เขียน และ `main` ถูกป้องกันไว้ ส่วน Level 3 ในหัวข้อ 1 ต้องมีผู้รีวิว 2 คน
- **Static analysis ใน CI:** ESLint + Prettier, `tsc --strict`, `npm audit`, Semgrep และ dependency-cruiser (NFR-12 ห้าม import ข้ามโมดูล) รันทุก PR ถ้าไม่ผ่านจะ merge ไม่ได้ ส่วน NFR-05 (hash รหัสผ่าน) ทวนสอบด้วยการตรวจพินิจโค้ด

## 4. สิ่งที่ตั้งใจไม่ทดสอบ และเหตุผล

| ไม่ทดสอบ | เหตุผล |
|---|---|
| การให้คะแนน/ตัดสินผล AUN-QA, AI เขียน SAR, OCR, แอป Native, การเชื่อม API กับระบบมหาวิทยาลัยและ SSO | อยู่นอกขอบเขตตาม SRS 1.2 จึงไม่มีโค้ดให้ทดสอบ |
| ระบบของทีม P3–P6 | ทดสอบเฉพาะรูปแบบแพ็ก CSV/JSON ที่รับเข้าด้วย fixture ไม่ทดสอบระบบต้นทาง |
| ภายในไลบรารีบุคคลที่สาม (React, Express, ORM, ตัวสร้าง PDF) | เชื่อถือผู้พัฒนาไลบรารี ทดสอบเฉพาะส่วนที่เราใช้ผ่าน integration test |
| ความถูกต้องเชิงวิชาการของ Mapping (เช่น ควรเป็น R หรือ M) | เป็นการตัดสินของกรรมการหลักสูตร ระบบทวนสอบได้เพียงว่าคำนวณและแสดงตามข้อมูลที่ใส่อย่างถูกต้อง |
| ข้อมูลส่วนบุคคลจริงของนักศึกษา/บุคลากร | ใช้ข้อมูลสังเคราะห์ทั้งหมด (สอดคล้องกับ D12) |

**ข้อจำกัดที่ต้องติดตาม:** NFR-03 (100 ผู้ใช้), NFR-04 (HTTPS) และ NFR-09 (กู้คืน) ต้องวัดบนเครื่องที่ติดตั้งจริง ถ้า TBD-06 ยังไม่ได้ข้อยุติก่อน CP4 จะวัดบนเครื่องทดสอบที่บันทึกสเปกไว้ และระบุผลเป็นข้อจำกัดในรายงาน
